OAUTH 2.0 (Open Authorization)

Imagine you are staying at a hotel, and you want to order a pizza. The delivery driver arrives at the front desk, but the hotel won’t let them up to your room. You don’t want to give the driver your actual room key (that would be dangerous – they could steal your stuff!)
Instead, you call the front desk and say, “Give the driver a temporary, restricted keycard that only works for the elevator and my floor, and make it expire in 15 minutes.”

That is OAuth. It is a protocol that allows a user to grant a third-party application (the driver) temporary, restricted access to their data (the hotel room) without ever giving the application their actual password (the master key).
Every time you click “Log in with Google” or allow a game to post to your Facebook timeline, you are using OAuth.


The CS Reality (Roles in OAuth 2.0)

OAuth 2.0 introduces four specific roles:

1. Resource Owner: You (the user).

2. Client: The third-party app you want to use
   (e.g., a Spotify app trying to read your Google Contacts).

3. Authorization Server: The bouncer
   (e.g., Google’s login server).

4. Resource Server: The database holding
   your data (e.g., Google Contacts API).


Authorization Code Flow (Step by Step)

1. The Request

The Client (Spotify) redirects your browser
to the Authorization Server (Google). The URL
includes what they want: scope=read_contacts
and a client_id telling who they are.

2. User Consent

You log into Google directly. Google shows a
screen: “Spotify wants to read your contacts.
Allow?” You click “Yes”. Spotify never sees
your password.

3. The Authorization Code

Google redirects your browser back to Spotify,
attaching a temporary, single-use string called
an Authorization Code to the URL.

4. The Code Exchange (Backend-to-Backend)

Spotify’s backend takes that Code and makes
a hidden, secure server-to-server request to
Google. It says, “Here is the user's Code, and
here is my secret API key proving I am really Spotify.”

5. The Access Token

Google verifies the Code and Secret Key, and
responds with an Access Token (usually a JWT).
Spotify can now use this token to fetch your
contacts from the Resource Server.


Pros, Cons, and Use Cases

Where we use it:

“Log in with Google/Apple/Facebook”
buttons (SSO), giving CI/CD pipelines
access to GitHub repos, connecting
bank accounts to budgeting apps
like Plaid.

Why we use it:

Delegated Access. Users shouldn’t
have to create a new password for
every website, and they should never
give their banking password to a third-party app.

Pros:

High security. The third-party app
never sees the user's password.
The user can revoke the app's
access at any time from their
Google dashboard.

Cons:

Extremely complex to implement
correctly. It introduces multiple
network hops (redirects) which
can cause latency or break if not
handled well on mobile apps.


How to Answer in an Interview

Q: What is OAuth 2.0, why do we use it, and how does the Authorization Code flow work?

Your Answer:

“OAuth 2.0 is an industry-standard authorization protocol that allows a user to grant a third-party application limited access to their resources without exposing their credentials. We use it to enable secure Single Sign-On (SSO) and delegated access.

In the Authorization Code flow, the client app redirects the user to the Authorization Server. The user authenticates and consents, and the server redirects back to the client with a short-lived Authorization Code. The client’s backend then securely exchanges this Code, along with its secret API key, for an Access Token.

This two-step process ensures the Access Token is never exposed to the user’s browser, preventing interception via cross-site scripting.”

SDE System Design Questions (What More Can Be Asked)


1. The Implicit Flow Flaw: “Why did we stop using the ‘Implicit Flow’ for frontend-only apps like React or Angular?”

The SDE Answer:

“In the old Implicit Flow, the Authorization Server returned the Access Token directly in the URL redirect hash (e.g., #access_token=...) without requiring a backend to exchange a code. This was highly insecure because the token was exposed in browser history, HTTP referer headers, and was vulnerable to XSS attacks. Today, we use the Authorization Code flow with PKCE (Proof Key for Code Exchange) to secure mobile and Single Page Applications.”

2. Authentication vs Authorization: “Is OAuth 2.0 an authentication protocol?”

The SDE Answer:

“Technically, no. OAuth 2.0 is strictly an authorization protocol—it grants access to resources. However, it is heavily used for authentication by layering OpenID Connect (OIDC) on top of it. OIDC standardizes the OAuth flow to return a specific ID Token (a JWT) that contains the user’s identity data, bridging the gap between authorization and authentication.”


OAuth 2.0 (Authorization)

• Grants access to resources
• Does not handle user identity
• Used to access APIs
  (e.g., Google Drive, GitHub)


OpenID Connect (Authentication)

• Built on top of OAuth 2.0
• Returns an ID Token (JWT)
  with user identity data
• Used for authentication
  (e.g., “Log in with Google”)


3. The Refresh Token: “What happens when the Access Token expires in 1 hour?”

The SDE Answer:

“During the initial code exchange, the Auth Server usually returns both an Access Token and a long-lived Refresh Token. When the Access Token expires, the backend client silently sends the Refresh Token to the Auth Server to get a new Access Token, preventing the user from having to log in again. If the user revokes the app’s permission, the Refresh Token is invalidated.”


Refresh Token Flow

1. Send Refresh Token
   (to get new Access Token)

2. New Access Token
   (returned)

• Initial code exchange returns Access Token + Refresh Token
• Use Refresh Token when Access Token expires
• If user revokes access, Refresh Token is invalidated


The Delegation Problem

The Delegation Problem is the fundamental security challenge that OAuth was invented to solve.

The Analogy:

You park your car at a high-end restaurant and hand your keys to the valet. The valet needs your key to drive the car into the parking garage. However, because you gave them your master key, they also have the power to open your glovebox, steal your GPS, or drive the car to another state.

In software, how do you give a third-party app (the valet) permission to do one specific task on your behalf without giving them your master password?

This evolves into a famous security vulnerability known as the Confused Deputy Problem.


The CS Reality (The Confused Deputy Problem)

A “Deputy” is a computer program that has high-level permissions.

The “Confused Deputy Problem” happens when a hacker tricks that highly privileged program into misusing its authority to do something the hacker isn’t allowed to do.

Let’s look at an example in a microservices architecture:

1. The Setup: You build a “Billing Service” that has root access to the database to generate invoices.

2. The Attack: A hacker (User A) sends a request to the Billing Service saying, “Generate an invoice, and write the output file over User B’s private tax documents.”

3. The Failure: The Billing Service blindly trusts the request. Because the Billing Service itself has root permission to modify User B’s files, it overwrites the file. The hacker didn’t have permission to modify User B’s files, but they tricked the “Deputy” (the Billing Service) into doing it for them.

Request Context in Backend Applications

1. What Is Request Context?

Request context is the collection of information and state associated with a particular HTTP request while the backend processes it.

For example, imagine you're building a website where users can log in, view their profiles, and purchase products.

When a user requests their profile, the backend might need to know:
- Who is making the request?
- Which URL are they accessing?
- Which HTTP method are they using?
- What data did they send?
- What authentication token did they provide?
- What is their request ID?
- Which database operation should be performed?

The backend needs this information to process the request correctly.


2. Example

Suppose your frontend sends this request:

GET /api/profile
Authorization: Bearer abc123
X-Request-ID: req-789

The backend receives a request containing information such as:

{
    method: "GET",
    path: "/api/profile",
    headers: {
        authorization: "Bearer abc123",
        "x-request-id": "req-789"
    },
    user: null
}

Initially, the backend might not know which user owns the token.
After authentication middleware verifies the token, it can associate the authenticated user with the request.

The resulting request-associated information might look conceptually like this:

{
    method: "GET",
    path: "/api/profile",
    requestId: "req-789",
    user: {
        id: 101,
        role: "user"
    }
}

This is a simplified illustration, not a standardized request-context object. Different frameworks implement request context differently.

Important: Request context is not the same as the HTTP request itself. The HTTP request contains the information sent by the client, while request context can also include information created by the backend during processing.


3. What is a Request Context, and how do you implement it in a Node.js backend to trace a request across multiple microservices?

Your Answer:

"A Request Context is the state or metadata scoped to the lifecycle of a single incoming HTTP request. It typically contains information like the authenticated User ID and a unique Correlation ID.

In standard Express applications, we build this context using middleware by mutating the req object (e.g., req.user = decodedToken). However, to avoid 'prop drilling' this context down into the Service and Repository layers, I prefer using Node's AsyncLocalStorage. By wrapping the request in an AsyncLocalStorage.run() block at the middleware level, any deep internal service can retrieve the trace ID statelessly. To trace this across multiple microservices, I would ensure that the outgoing HTTP client reads that trace ID from the context and injects it into the x-correlation-id header of any downstream requests, allowing our distributed logging system to stitch the entire journey together."

5. Implementing Request Context in Node.js (Express)

Using AsyncLocalStorage

const { AsyncLocalStorage } = require('async_hooks');
const asyncLocalStorage = new AsyncLocalStorage();

app.use((req, res, next) => {
    const requestId = req.headers['x-request-id'] ||
        crypto.randomUUID();

    asyncLocalStorage.run(
        { requestId, user: null },
        () => {
            next();
        }
    );
});

// Later in auth middleware
app.use((req, res, next) => {
    const user = verifyToken(req.headers.authorization);
    const context = asyncLocalStorage.getStore();

    if (context) {
        context.user = user;
    }

    next();
});

// In any deep service/repository
function getRequestContext() {
    return asyncLocalStorage.getStore();
}

const ctx = getRequestContext();
console.log(ctx.requestId, ctx.user);

AsyncLocalStorage allows any deep internal service to retrieve the request context without passing it explicitly (prop drilling).


6. Tracing Across Multiple Microservices

To trace the request across multiple microservices, we need to propagate the same correlation ID in outgoing requests.

Client
    |
    | x-correlation-id: abc-123
    v
Service A (API Gateway)
    |
    | x-correlation-id: abc-123
    |
    +----------------------+
    |                      |
    v                      v
Service B                Service C
(User Service)           (Order Service)

The outgoing HTTP client reads the correlation ID from the context and injects it into the x-correlation-id header of downstream requests.

const axios = require('axios');

async function callUserService() {
    const ctx = asyncLocalStorage.getStore();

    return axios.get('http://user-service/api/user', {
        headers: {
            'x-correlation-id': ctx.requestId
        }
    });
}

All microservices use the same x-correlation-id for distributed logging, so our logging system can stitch the entire journey together.


7. Key Points to Remember

- Request context is the state or metadata associated with a single HTTP request while the backend processes it.
- It includes information like the user, request ID, method, path, headers, etc.
- It is not the same as the HTTP request itself.
- In Node.js, we can implement it using middleware and AsyncLocalStorage.
- AsyncLocalStorage avoids prop drilling and allows deep internal services to access the context.
- To trace across microservices, propagate a correlation ID (e.g., x-correlation-id) in outgoing requests.
- This helps in distributed logging and debugging.


Advanced Interview Questions on Request Context (Node.js)

1. The Context Loss Trap (Deep Node.js)

The Interviewer asks:
"You mentioned AsyncLocalStorage creates an invisible bubble around the request you love. Have you ever experienced a situation where you try to call requestContext.getStore() deep in your service layer, and it suddenly returns undefined? Why does that happen?"

The SDE Answer:
"Yes, this is known as 'Context Loss'. AsyncLocalStorage relies on Node.js's underlying async_hooks API to track the execution thread across asynchronous boundaries (like Promises and setTimeout). However, the context bubble can break if you bridge across certain event emitters, traditional callbacks without properly binding them, or if you use connection pools that queue tasks externally. If a task is handed off to a thread pool or a third-party library that doesn't properly propagate the async resources, the link breaks. To fix it, we have to explicitly bind the context using AsyncResource.bind() before passing the callback into the black-box library."


2. The Security & Spoofing Trap

The Interviewer asks:
"You said you extract the Trace ID or Correlation ID from the incoming HTTP request headers (e.g., x-correlation-id) to track the request. What if a malicious user intentionally sends a fake or conflicting x-correlation-id in their browser request? Doesn't that corrupt our logs?"

The SDE Answer:
"If we blindly trust external client headers, yes, it corrupts our tracing data. To secure the context, our API Gateway (or the very first Edge Middleware) must act as the source of truth. The rule is: we completely strip and ignore any x-correlation-id sent from the public internet. The Edge Gateway will securely generate a fresh UUID and inject it into the header. From that point on, our internal microservices will trust the header because it was generated safely inside our private network."


3. The Performance Overhead Trap

The Interviewer asks:
"Is there any downside to using AsyncLocalStorage? Why wouldn't we just pass the traceId down through the function parameters (prop drilling), even if it makes the code a bit uglier?"

The SDE Answer:
"The trade-off is CPU performance versus Developer Experience. AsyncLocalStorage hooks into Node's V8 engine to track every single async operation. This introduces a slight CPU and memory overhead. For 99% of enterprise applications, this overhead is practically invisible, and the benefit of having clean, decoupled code without prop-drilling is entirely worth it. However, if we were building an ultra-low-latency system — like a high-frequency trading platform where every microsecond counts — we would avoid AsyncLocalStorage and revert to strict prop-drilling to maximize V8 engine performance."


4. The Microservice Log Aggregation Trap

The Interviewer asks:
"Okay, you successfully attached the traceId to the Request Context, and you used it in your console.log() statements. But we have 50 different microservices running on 50 different servers. How do you actually use this ID to debug a problem?"

The SDE Answer:
"Printing the Trace ID to the local server console isn't enough in a distributed system. First, when our Service Layer makes an HTTP call to a downstream microservice, we must ensure our HTTP client (like Axios) reads the traceId from the AsyncLocalStorage context and injects it into the outbound HTTP headers. Second, instead of just printing to the console, our logs must be shipped asynchronously to a centralized Log Aggregation platform like Datadog, ELK stack (Elasticsearch, Logstash, Kibana), or Splunk. When an error occurs, we can paste that single Trace ID into Kibana and instantly pull up a chronological timeline of every log from every single microservice that handled that specific user's request."

Fix using AsyncResource.bind()

const { AsyncResource } = require('async_hooks');
const asyncResource = new AsyncResource('MY_TASK');

someLibrary.on('event', asyncResource.bind(() => {
    // This callback will now have the correct context
    const ctx = requestContext.getStore();
    // ctx is available here
}));

AsyncResource.bind() explicitly binds the current async context to the callback before passing it to the black-box library.

AsyncLocalStorage vs Prop Drilling

AsyncLocalStorage:
- Slight CPU and memory overhead (tracks every async operation)
- Clean, decoupled code (no prop-drilling)
- Easy to access context in any deep layer
- Suitable for 99% of enterprise applications
- Uses Node's async_hooks and V8 to track context

Prop Drilling (Function Parameters):
- No additional runtime overhead
- Requires passing traceId through every function (ugly code)
- Tight coupling between layers
- More boilerplate code
- Preferred only for ultra-low-latency systems (e.g., high-frequency trading) where every microsecond counts
